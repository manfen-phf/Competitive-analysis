# P0-2 BD 采集设计

## 目标

让已导入的 BD 以最少操作完成一次可追踪的双平台订单采集：选择自己的身份、选择名下商家、同时上传美团与 B 家订单长图。

## 方案选择

采用签名会话而不是完整账号密码体系。导入时创建的 BD 名称作为内部身份入口；服务端签发仅含 BD 用户 ID 的 HttpOnly 签名会话，所有商家与上传接口都基于该 ID 查询。这样满足 V1 的“BD 仅看自己的商家”，且不增加外部身份平台或账号维护负担。

## 采集数据流

1. BD 在 `/collect` 选择已激活的姓名，服务端签发会话。
2. 前端从 `/api/bd/merchants` 获取该 BD 当前有效的商家，可按城市、ID、名称检索。
3. BD 选择一个商家，同时提交 `meituanFile` 与 `bJiaFile`。
4. 服务端校验文件格式、大小、商家归属、两图哈希和历史重复上传。
5. 服务端先保存两张原图至 R2，再批量写入 `CollectionSession` 和两条 `UploadImage` 记录至 D1；写库失败时删除刚创建的 R2 对象。
6. 会话状态为 `UPLOADED`，留给 P0-3 触发千问识别与人工确认。

## 数据边界

- 一个 `CollectionSession` 代表一个 BD、一个商家、一次采集任务。
- 每个任务必须有且仅有美团与 B 家各一张图。
- D1 只保存 R2 Key、哈希、MIME 类型和业务元数据；原图不写进 D1。
- 同一图像哈希全局只能采集一次，既避免重复识别也能支持未来原图清理策略。

## 非目标

- 不做千问调用、人工确认、指标对比、统计、导出。
- 不增加企业 SSO、密码体系或成员管理功能。

## 验收

- BD 无法读取其他 BD 的商家。
- 非法文件、缺少任一平台图、重复图、非名下商家均被拒绝。
- 成功采集后 D1 有 1 条任务和 2 条图片记录，R2 有 2 个对象。
